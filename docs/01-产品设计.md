# 01 · 产品设计

> 这份文档定义 Routebook 是什么、为谁做、做成什么样。
> **后面所有的技术决策，都是从这份文档推导出来的。** 改产品定义之前，先想清楚会影响哪些技术部分。

---

## 1. 一句话定位

**Routebook 是一个自我驱动的学习助手：它把一门知识拆成带依赖关系的节点网络，记录你真实走到哪一步，然后持续告诉你下一步该去哪、该做什么。**

它不是博客，不是笔记软件，也不是课程平台。

| 它不是什么 | 区别在哪 |
|---|---|
| 不是博客 | 博客按时间倒序陈列内容；Routebook 按**依赖关系**组织内容 |
| 不是笔记软件 | 笔记软件不管你怎么学；Routebook 关心你的**进度和下一步** |
| 不是课程平台 | 课程平台给你一条固定跑道；Routebook 的路线由**你自己定义和演化** |
| 不是 ChatGPT 套壳 | 通用聊天机器人不知道你的进度；Routebook 每句话都基于你的**进度快照** |

## 2. 要解决的问题

### 2.1 核心痛点

学习 AI 大模型应用开发这类新兴技术时，有三个具体的痛：

1. **资料爆炸，不知道从哪开始。** 同一个主题有 50 篇教程、20 个视频、3 本书，看完目录就累了。真正稀缺的不是资料，是**筛选和排序**。
2. **学完就忘，学了不知道有没有用。** 今天看完 RAG 的教程，明天就记不清 rerank 是干嘛的，而且无法判断自己到底掌握了没有。
3. **没有外部反馈，全靠自律。** 自学最大的敌人是"今天要不要继续"这个每天都要重新回答一次的问题。没有人问你进度，也没有人告诉你可以开始了。

### 2.2 现有方案为什么不够

| 现有方案 | 为什么不够 |
|---|---|
| 收藏夹 / 文章列表 | 只解决"存"，不解决"排序"和"下一步" |
| 通用 AI 聊天 | 每次对话都失忆，不知道你的进度，只能给通用建议 |
| 网课平台 | 路线固定，进度是"看完视频"而不是"学会了" |
| 笔记软件 + 打勾清单 | 有进度没有依赖关系，无法回答"学完 A 之后该学 B 还是 C" |

### 2.3 Routebook 的解法

三个关键设计决策，对应三个痛点：

| 痛点 | 解法 | 落在哪个模块 |
|---|---|---|
| 不知道从哪开始 | **依赖关系图** + 基于前置完成的下一步推荐 | 路线引擎 |
| 学完就忘、不知是否掌握 | **出口条件** 强制验收 + **间隔重复** 复习调度 | 进度引擎 |
| 缺乏外部反馈 | **AI 学习助手**主动给出下一步和任务编排 | 助手模块 |

## 3. 目标用户

### 3.1 主要用户（阶段一）

**正在自学某个技术领域的开发者。**

特征：
- 有一定编程基础，能看懂代码
- 学习目标明确（如"掌握 AI 应用开发"），但路径模糊
- 习惯用 Markdown 记笔记
- 愿意每天花 30–120 分钟学习
- 技术上是"单用户"，自己用

### 3.2 明确不服务的场景（非目标）

写清楚"不做什么"和"做什么"同样重要，避免范围蔓延：

- ❌ **不做多人协作学习**（阶段一不做。但数据模型预留 `user_id`，见 `02`）
- ❌ **不做内容平台**：不提供别人写好的课程，路线完全由用户自己定义
- ❌ **不做题库、考试系统**：出口条件由用户自己写，系统只负责记录和验证是否通过
- ❌ **不做移动端 App**：响应式 Web 即可
- ❌ **不做社区、评论、分享**（V2 再议）

## 4. 核心概念（术语表）

> **这是全套文档最重要的表。** 后面所有文档出现的这些词，含义都以这里为准。

| 术语 | 英文 / 字段名 | 定义 |
|---|---|---|
| **路线** | Route | 一个学习主题的完整知识网络。例如"AI 大模型应用开发"。一个用户可以有多条路线 |
| **节点** | Node | 路线上最小的学习单元，一个可独立学习和验收的知识点。例如"向量与相似度" |
| **依赖** | Dependency | 节点之间的有向边 A → B，表示"学 B 之前应该先掌握 A"。**这是整个产品的灵魂** |
| **前置节点** | Prerequisite | 某个节点的所有直接依赖节点 |
| **出口条件** | Exit Criteria | 一段文字描述"做到什么才算真的掌握这个节点"。例如"能说出余弦相似度在干什么" |
| **进度** | Progress | 某用户在某节点上的状态记录，一个 (用户, 节点) 二元组 |
| **状态** | Status | 进度的枚举值：`not_started` / `learning` / `mastered` / `needs_review` |
| **掌握度** | Mastery | 0–5 的整数，主观自评的熟练程度。与状态互补：状态是"阶段"，掌握度是"程度" |
| **出口条件通过** | — | 用户自评"达成了出口条件"才能把状态改为 `mastered`。系统不做客观判定（V1），只做提醒 |
| **复习衰减** | Review Decay | 已掌握节点会随时间"变旧"，到达复习时间点自动转为 `needs_review` |
| **间隔重复** | Spaced Repetition | 复习间隔按 1 → 3 → 7 → 15 → 30 → 60 天递增的调度算法 |
| **笔记** | Note | 挂在节点上的一篇 Markdown 文本。一个节点一篇（一对多预留，见 `02`） |
| **资源** | Resource | 挂在节点上的一条学习资料指引（名称 + 在哪找）。**刻意限制每节点 1–2 条** |
| **任务** | Study Task | AI 或用户编排出来的一件具体待办，带截止日期 |
| **会话** | Conversation | 用户与 AI 助手的一次连续对话 |
| **消息** | Message | 会话中的一条记录，角色为 user / assistant / system |
| **上下文快照** | Context Snapshot | 每次请求 AI 时，把用户当前进度序列化成的结构化数据。**这是"助手懂你"的全部秘密** |
| **异步作业** | AI Job | 一次耗时的 AI 调用记录，有独立的生命周期和状态 |

### 4.1 几个容易混淆的地方

**状态（Status） vs 掌握度（Mastery）**

- 状态回答"你现在处在哪个阶段"：还没开始 / 正在学 / 掌握了 / 该复习了
- 掌握度回答"你有多熟"：5 分是能给别人讲，1 分是刚看完还有点懵
- 两者都要有。只有状态会变成"打勾游戏"；只有掌握度就无法驱动流程

**出口条件 vs 复习**

- 出口条件是**进门门槛**：达成它才能标为 `mastered`
- 复习是**维护成本**：标为 `mastered` 之后，系统按间隔重复提醒你回来

**笔记 vs 资源**

- 资源是**别人写的**（教程、论文、文档），指向外部
- 笔记是**你自己写的**，存在系统内
- 二者都挂在节点上，但用途完全不同：资源用来学，笔记用来固化

## 5. 核心场景

### 场景 A：第一次使用，建立路线

1. 用户打开 Routebook，页面提示"你还没有任何路线"
2. 用户选择一种方式创建：
   - **从模板创建**：系统内置几条现成路线（如附录 A 的「AI 大模型应用开发」，26 个节点），一键导入
   - **空白创建**：自己逐个添加节点
   - **AI 生成**（V1）：输入主题，AI 生成一份候选路线草稿，用户逐条审阅后再固化
3. 建好后，用户看到完整的路线图，所有节点状态为 `not_started`

> **设计原则：AI 生成的路线必须经过人工审阅才能入库。** 路线是静态资产，一旦固化就很少变动；AI 每次现生成会导致路线漂移（今天让学 A，明天让学 B），这是必须避免的。

### 场景 B：日常学习循环（最核心）

1. 用户打开首页，看到进度概览
2. 点击「下一步学什么」
3. 系统返回 1–3 个推荐节点，每个附带：
   - 为什么推荐它（"前置已完成：大模型关键概念、Python 工程能力"）
   - 它的出口条件
   - 1–2 条推荐资源
4. 用户点开某个节点，把状态改为 `learning`
5. 用户去外部找资料学习（Routebook 不负责教学，只负责指路）
6. 学完回来，用户：
   - 写下笔记（用自己的话复述）
   - 自评掌握度
   - 如果认为达成了出口条件，把状态改为 `mastered`
7. 系统记录掌握时间，安排首次复习时间

> **这个循环是产品的全部。** 其他所有功能都是围绕它做增强。如果这个循环不顺畅，其他功能做得再花哨都没意义。

### 场景 C：AI 助手深度介入

用户在「下一步」面板上点「让助手解释一下」，或者直接在对话里问：

> "我学完 Embedding 了，但向量数据库看得有点懵，接下来走哪条路比较好？"

系统做的事情：

1. **组装上下文快照**：读取当前路线结构、用户全部进度、该节点及其前置节点、最近笔记摘要
2. **调用 LLM**，附带严格的输出格式约束
3. **返回结构化建议**：推荐的下一步节点（必须是路线中真实存在的节点 ID）、理由、预计难度、建议的先修补内容
4. 用户可以直接把建议转为任务

> 关键：助手**不能凭空创造路线外的节点**。它的输出被约束在已有路线之内，这是通过输出校验强制保证的（见 `06-AI能力设计.md`）。

### 场景 D：复习与衰减

1. Celery 定时任务每天凌晨扫描所有 `mastered` 节点
2. 对超过复习间隔的节点，状态自动转为 `needs_review`
3. 用户下次打开时看到"有 3 个节点该复习了"
4. 用户复习后点击"还记得"或"忘了"：
   - 还记得 → 间隔翻倍，状态回到 `mastered`
   - 忘了 → 间隔重置为 1 天，掌握度降 1，状态回到 `needs_review`

### 场景 E：任务编排

用户说："帮我安排这周的学习。"

系统：
1. 读取可推进的节点（前置已完成、自己未开始）
2. 结合用户的自定义约束（每天可学时长、偏好工作日还是周末）
3. 调用 LLM 生成一个周计划
4. 落库为若干 `study_task` 记录，带 `due_date`
5. 首页显示"今日任务"

## 7. 关键交互设计原则

这几条是设计约束，前端实现时必须遵守：

1. **一屏内能完成一次学习循环。** 推荐 → 打开节点 → 写笔记 → 标记掌握，全程不跳页。
2. **进度必须随手可改，且可撤销。** 点一下圆圈即可流转状态，点错了能立刻点回来。**不要弹确认框**。
3. **依赖未满足时给提示，但不要禁止操作。** 用户可能已经会了，系统只做建议，不做拦截。
4. **AI 的建议必须附上理由。** 只给结论（"学 X"）是无效的；给出"因为你的 A 和 B 已完成"才有价值。
5. **AI 的失败不能阻塞核心流程。** LLM 超时或报错时，规则版推荐必须照常工作。**这是硬要求，见 `06-AI能力设计.md` 的降级策略。**
6. **不要太漂亮。** 这个产品的敌人是"打磨工具花掉三个月，一个知识点没学"。克制视觉投入。

## 8. 成功标准

怎么判断这个产品做成了？

### 8.1 产品的成功标准

| 指标 | 目标 | 为什么定这个 |
|---|---|---|
| 核心循环可用性 | 从打开到标记掌握，操作步骤 ≤ 5 步 | 步骤多一步，每天少用一次 |
| 数据安全性 | 全量可导出，格式为开放标准（JSON + Markdown） | 不锁定用户 |
| AI 可用性 | LLM 完全不可用时，产品核心功能仍 100% 可用 | 见交互原则 5 |
| 依赖图正确性 | 任何时刻不存在环；非法依赖操作 100% 被拒绝 | 有环则推荐算法失效 |

### 8.2 这个项目对你（开发者）的成功标准

**这个项目的首要目标，是让你学会 AI 应用开发。产品是学习过程的产物，不是目的。**

所以：

- ✅ **成功 = 你通过做这个项目，真正掌握了 RAG、Agent、上下文工程**
- ❌ **失败 = 你花了三个月做出了完美的路线图 UI，但一个知识点没学**

对应的执行约束，写在 `08-开发计划.md` 里：**每个里程碑对应的技术主题，必须是你已经学过或正在学的。**
