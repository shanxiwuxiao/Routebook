## 执行纪律

**三条铁律，违反任何一条都算项目失败（见 `01-产品设计.md` §8.2）：**

1. **每个里程碑开始前，先确认你已学会它对应的学习节点。** 没学会就先学，别急着写代码。
2. **每个里程碑结束时，验收标准必须全部通过。** 不通过就修，不进入下一个。
3. **不允许提前做后面里程碑的功能。** 看到 M7 才需要 RAG，就不要在 M3 就开始装向量库。

**为什么纪律这么严**：这个项目最大的风险不是技术难度，是"造工具三个月、一个知识点没学"。里程碑的作用是把"做项目"和"学知识"强行绑在一起。

### 涉及的技术

| 技术 | 要点 |
|---|---|
| SQLAlchemy 2.0 async | `AsyncSession`、`select()` 新语法、关系加载策略 |
| Alembic | autogenerate 的盲区、手工写迁移 |
| PostgreSQL | 递归 CTE、`FILTER` 聚合、部分索引、触发器 |
| pgvector | `vector(1536)` 类型、HNSW 索引、`<=>` 运算符 |
| pytest-asyncio | 异步测试的 fixture 写法 |

### 验收标准

**迁移**

- [ ] `uv run alembic upgrade head` 成功执行
- [ ] **`uv run alembic downgrade base` 再 `upgrade head` 成功**（迁移可逆！）
- [ ] 用 `psql` 连进数据库，`\dt` 能看到全部 13 张表
- [ ] `\d chunks` 能看到 HNSW 索引
- [ ] `SELECT * FROM pg_extension;` 能看到 vector、pgcrypto、pg_trgm

**种子数据**

- [ ] `uv run python -m routebook.db.seed` 成功
- [ ] **再执行一次，数据不重复**（幂等性）
- [ ] 数据库中有 1 个用户、1 条路线、26 个节点
- [ ] 依赖关系正确：`llm-api` 的 `depends_on` 包含 `python-eng` 和 `llm-concept`

**Repository 测试**

- [ ] `list_startable()` 返回的节点，其所有前置状态都是 `mastered`
- [ ] 没有任何前置时也能正确返回（起点节点）
- [ ] `would_create_cycle()` 对直接环（A→B，再 B→A）返回非空
- [ ] 对间接环（A→B→C，再 C→A）返回非空
- [ ] **对菱形依赖（A→B, A→C, B→D, C→D）返回空**（这不是环！）
- [ ] `list_with_progress()` 只执行固定条数的 SQL（用 SQLAlchemy 事件监听器数一下，**不能随节点数增长**）

### 常见坑

| 坑 | 后果 | 避免 |
|---|---|---|
| autogenerate 漏掉触发器 | 触发器不存在，资源上限失效 | **手工检查迁移文件**，`02` 里明确列了哪些必须手写 |
| 忘记 `CREATE EXTENSION vector` | 建表时 `vector` 类型报错 | 放在迁移第一步 |
| `embedding` 维度写错 | 插入时报维度不匹配 | 维度必须与 `EMBEDDING_DIM` 一致 |
| 测试用生产数据库 | 数据被清空 | 测试配置独立的库名，`conftest.py` 里断言 |
| 递归 CTE 没加深度限制 | 有环时数据库卡死 | `02` §4.6 的 `depth < 10` |
| 依赖查询 N+1 | 26 个节点查 27 次 | 用 `selectinload` 或一次性 JOIN |

### 里程碑检查点

**做完 M1 后，你应该能回答：**

1. 为什么 `node_progress` 要懒创建，而不是给每个节点预插记录？
2. `list_startable` 里的 `NOT EXISTS` 换成 `COUNT(*) = 0` 会有什么问题？
3. 为什么环检测不能用数据库约束做？

答不上来就回去看 `02-领域模型与数据库设计.md`。**这几个问题会在 M4 和 M5 反复出现。**

| 技术 | 要点 |
|---|---|

### 验收标准

- [ ] 掌握后 `review_due_at` 被设置为 `mastered_at + 1 天`

**笔记**

- [ ] 输入后 800ms 自动保存，显示"已保存"
- [ ] 刷新页面内容还在
- [ ] **快速连续输入不会产生多个请求**（网络面板观察）
- [ ] **边打字边切页面，内容不丢**（`beforeunload` 生效）
- [ ] 粘贴 10 万字内容，返回 422 并有友好提示

**并发**

- [ ] 连点状态圆圈 5 次，只产生合理的请求数（不是 5 个乱序请求）
- [ ] 最终状态与最后一次点击一致

### 常见坑

| 坑 | 后果 | 避免 |
|---|---|---|
| 无防抖 | 每敲一个字发一个请求 | 800ms 防抖 |
| 无 AbortController | 慢请求后到，覆盖新内容 | 保存前 abort 上一个 |
| 无失败回滚 | 状态显示"已掌握"但数据库里没有 | catch 里恢复 `previous` |
| 连点产生竞态 | 最终状态与最后一次点击不一致 | pending Map 去重 |
| 忘记 `beforeunload` | 用户关页面丢最后一段 | `onBeforeUnmount` + `beforeunload` 双保险 |

### 里程碑检查点

- [ ] 返回的 `reason` 字段**引用了用户的实际进度**（比如提到"你的 XX 已掌握"）
- [ ] 返回的 `node_id` **全部**是数据库中真实存在的节点
- [ ] 响应时间 P95 < 5 秒

**降级（每一条都要实测）**

- [ ] `AI_NEXT_STEP_ENABLED=false` → `source: "rule"`，功能正常
- [ ] 把 `AI_NEXT_STEP_TIMEOUT_SECONDS` 设成 `0.001` → `source: "rule"`，功能正常
- [ ] 把 API Key 改成错的 → `source: "rule"`，功能正常，且**没有把错误抛给前端**
- [ ] 在 FakeProvider 里让它返回幻觉 ID → 日志有 `ai.degraded`，返回 `source: "rule"`
- [ ] 连续失败 3 次后 → 熔断打开，**后续请求不再调用 LLM**（查日志确认没有新的 LLM 调用）

**成本与安全**

- [ ] 日志中能看到每次调用的 token 数
- [ ] `/stats/overview` 的 `ai_usage` 有数字
- [ ] `docker compose logs backend | grep -i "sk-"` **无输出**（Key 未泄露到日志）
- [ ] `docker compose logs backend | grep "prompt"` 显示的是 `<redacted>`（prompt 未泄露）

**测试**

- [ ] 所有 AI 相关测试用 `FakeLLMProvider`，无真实 API 调用
- [ ] 覆盖 `06-AI能力设计.md` §9.2 列出的全部 6 个降级测试用例
- [ ] `ContextBuilder` 的快照包含所有状态分类，且 `startable` 与 `blocked` 无交集

### 常见坑

| 坑 | 后果 | 避免 |
|---|---|---|
| 用真实 API 跑测试 | 测试慢、花钱、不稳定 | 全部用 FakeProvider |
| prompt 硬编码在 Python 里 | 改 prompt 产生代码 diff 噪音 | 独立 `.md` 文件 |
| 只靠 prompt 约束不校验 | 幻觉 ID 直接返回给前端 | 三层校验 |
| `asyncio.wait_for` 包错位置 | 超时没生效 | 包住整个 LLM 调用，不是包住 HTTP 请求 |
| 降级时抛异常给前端 | 用户看到报错弹窗 | 降级后正常返回，只记日志 |
| 不记 token 数 | 月底不知道花了多少钱 | 每次调用都记 |

| 历史无限增长 | 成本飙升、延迟变长 | `trim_history` |

### 涉及的技术

| 技术 | 要点 |
|---|---|
| RabbitMQ | exchange、routing key、队列绑定 |
| Celery | `acks_late`、`prefetch_multiplier`、超时、重试 |
| Celery Beat | 定时任务调度 |
| 幂等性 | `acks_late` 导致任务可能重复执行 |
| 异步桥接 | Celery（同步）调用 async service |
| 轮询 | 前端如何知道异步任务完成 |

### 验收标准

**基础设施**

- [ ] `docker compose logs worker` 显示 `celery@xxx ready`
- [ ] RabbitMQ 里有 3 个队列，每个都有 1 个 consumer
- [ ] Flower（`http://localhost:5555`）能看到 worker 在线

**任务执行**

- [ ] `POST /assistant/plan` 在 200ms 内返回 `job_id`
- [ ] 作业状态按 `queued → running → succeeded` 变化
- [ ] 完成后 `study_tasks` 表里有记录，且带 `due_date`
- [ ] 前端轮询能正确显示进度并展示结果

**幂等性**

- [ ] 手动把同一个 `job_id` 投递两次，**只执行一次**（第二次直接返回）
- [ ] worker 中途重启，作业最终仍能完成

**定时任务**

- [ ] `beat` 容器日志里有调度记录
- [ ] 手动把某节点的 `review_due_at` 设成昨天，等 `decay_review_status` 跑完，状态变成 `needs_review`
- [ ] 手动造一条 `running` 且 `started_at` 是 20 分钟前的作业，等 `cleanup_stale_jobs` 跑完，状态变成 `failed`

**超时与失败**

- [ ] 把 `task_time_limit` 设成 1 秒，投递 `generate_plan`，作业状态变成 `failed` 且有超时提示
- [ ] 让 LLM 调用失败，作业状态变成 `failed`，`error` 字段有可读的原因

**资源**

- [ ] `docker stats` 观察 worker 内存在多任务后不持续增长（`--max-tasks-per-child` 生效）

### 常见坑

| 坑 | 后果 | 避免 |
|---|---|---|
| 在 Celery task 里用 AsyncSession | 事件循环冲突，任务挂死 | 用同步 session（`SyncSessionLocal`） |
| 忘记 `asyncio.run()` | async service 在同步上下文里报错 | task 里用 `asyncio.run()` 包住 |
| 任务不幂等 | `acks_late` 导致重复执行，数据重复 | 以 `job_id` 为幂等键 |
| 没有 `task_time_limit` | 卡死的任务永久占用 worker | 必须设置硬超时 |
| worker 崩溃后作业卡在 running | 前端永远轮询 | `cleanup_stale_jobs` 定时任务 |
| 不配 `--max-tasks-per-child` | 内存泄漏累积到 OOM | 设 50 |

### 里程碑检查点

**M8 涉及的技术栈最多，也最容易卡住。** 如果卡住超过两天，先简化：

1. 先让 Celery 跑通一个最简单的 task（比如打印日志）
2. 再接 LLM
3. 最后做轮询

## 最后一句

**这个项目的第一目标是让你学会 AI 应用开发，产品是学习过程的产物。**

所以：

- 卡在某一步超过三天 → 停下来去学对应的知识点，而不是硬扛
- 想加新功能 → 先问"这对应哪个学习节点"，答不上来就不加
- 进度落后于计划 → 计划是假的，你学到的东西是真的，**不要为了赶进度跳过验收标准**

**最坏的结果是：你做出了一个漂亮的网站，但一个知识点没学。**
**最好的结果是：你学到了东西，顺便得到了一个自己天天在用的产品。**
