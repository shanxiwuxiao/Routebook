# 09 · 开发规范

> 规范的目的不是"让代码好看"，是**让你三个月后还能看懂自己写的代码**。
>
> 个人项目最常见的失败不是技术不会，是"改到一半发现前面写的看不懂了"。

---

## 1. Git 约定

### 1.1 提交信息格式

采用 Conventional Commits：

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

| type | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 重构（不改行为） |
| `perf` | 性能优化 |
| `docs` | 只改文档 |
| `test` | 只改测试 |
| `chore` | 构建、依赖、配置 |
| `style` | 格式调整（不改逻辑） |

**示例**

```
feat(progress): 支持状态循环切换与乐观更新

- 点击圆圈按 未开始 → 学习中 → 已掌握 循环
- 接口失败时自动回滚
- 使用 pending Map 防止连点竞态

Closes #12
```

```
fix(deps): 修复间接依赖环未被检测的问题

原实现只检查了直接依赖，A→B→C 再添加 C→A 时会漏检。
改为递归 CTE 查询传递闭包。

Fixes #18
```

**规则**

- subject 用中文或英文都行，但**同一个项目保持一致**
- subject 不超过 50 字，不以句号结尾
- **一个提交只做一件事**。如果 commit message 里出现了"并且"，说明该拆成两个提交

### 1.2 分支策略

个人项目用简化版 Git Flow：

```
main          ← 随时可部署
  └── dev     ← 开发主线
        └── feat/xxx    ← 功能分支
        └── fix/xxx     ← 修复分支
```

| 分支 | 规则 |
|---|---|
| `main` | 只接受来自 `dev` 的合并。每个合并点打 tag |
| `dev` | 日常开发。可直接提交 |
| `feat/*` | 一个里程碑或一个功能一个分支。完成后合回 `dev` |

**MVP 阶段可以简化**：直接在 `main` 上开发，功能完成时打 tag。但**从 M5 开始必须用分支**，因为 AI 部分调试周期长，需要能随时切回可用状态。

### 1.3 Tag 约定

```
v0.1.0    M0-M1 完成（能跑）
v0.2.0    M2-M3 完成（能用）        ← 第一个真正可用的版本
v0.3.0    M4 完成（MVP）
v0.5.0    M5-M6 完成（有 AI）
v0.7.0    M7-M8 完成（有 RAG 和异步）
v1.0.0    M10 完成（上线）
```

### 1.4 `.gitignore`

**必须包含（漏掉任何一个都可能造成事故）**：

```gitignore
# 环境变量 —— 绝对不能提交
.env

!.env.example

# Python
__pycache__/
*.py[cod]
.venv/
```

## 2. Python 规范

### 2.1 工具配置

**`backend/pyproject.toml`**

```toml

[tool.ruff.lint]

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["ARG", "S101"]     # 测试里允许不用参数、允许 assert

[tool.mypy]

[[tool.mypy.overrides]]

[tool.pytest.ini_options]

```

**`ASYNC` 规则组特别重要**：它会自动检出"在 async 函数里用了阻塞调用"这类问题，这正是 FastAPI 项目最容易翻车的地方。

### 2.2 命名约定

| 对象 | 约定 | 示例 |
|---|---|---|
| 模块 | `snake_case` | `node_repo.py` |
| 类 | `PascalCase` | `NodeRepository` |
| 函数/方法 | `snake_case` | `list_startable` |
| 常量 | `UPPER_SNAKE` | `MAX_RESOURCES_PER_NODE` |
| 私有 | 前缀 `_` | `_translate_error` |
| Pydantic 模型 | 后缀表示用途 | `NodeCreate` / `NodeUpdate` / `NodeOut` |
| SQLAlchemy 模型 | 单数 `PascalCase` | `NodeProgress`（表名由 `__tablename__` 指定为复数） |

**Schema 命名规则**（重要，避免混淆）：

| 后缀 | 用途 |
|---|---|
| `XxxCreate` | 创建时的请求体 |
| `XxxUpdate` | 更新时的请求体（字段全可选） |
| `XxxOut` | 响应体 |
| `XxxDetail` | 详情型响应（含嵌套） |
| `XxxBrief` | 简略型（只有 id + 标题这类） |

### 2.3 类型注解

**`mypy strict` 下，所有函数必须有完整注解。**

```python
# ❌
def find(id):
    ...

# ✅
def find(node_id: UUID, *, session: AsyncSession) -> Node | None:
    ...
```

**规则**

- 用 `X | None` 而不是 `Optional[X]`（Python 3.10+ 语法）
- 用 `list[str]` 而不是 `List[str]`
- **不用 `Any`**。实在不行用 `object` + 类型收窄
- 外部库返回的不可控类型，用 `cast()` 而不是 `# type: ignore`

### 2.4 异步规范

**这是 FastAPI 项目最关键的一条：全链路 async，不能混入阻塞调用。**

```python
# ❌ 阻塞事件循环
async def bad():
    time.sleep(1)                      # 整个服务卡 1 秒
    requests.get(url)                  # 同上
    open("f").read()                   # 大文件读取会卡
    engine = create_engine(...)        # 同步驱动

# ✅
async def good():
    await asyncio.sleep(1)
    async with httpx.AsyncClient() as c:
        await c.get(url)
    async with aiofiles.open("f") as f:
        await f.read()
    engine = create_async_engine(...)
```

**例外与处理**：

| 场景 | 处理 |
|---|---|
| 必须用同步库 | 用 `asyncio.to_thread()` 包装 |
| Celery task | Celery 本身是同步的，用同步 session 和 `asyncio.run()` 桥接 |
| CPU 密集计算 | `asyncio.to_thread()` 或独立的 worker 进程 |

```python
# 必须用同步库时的正确写法
result = await asyncio.to_thread(some_blocking_lib.call, arg1, arg2)
```

### 2.5 日志规范

**用 structlog，禁止 `print` 和 f-string 拼日志。**

```python
# ❌
print(f"用户 {user_id} 更新了节点 {node_id}")
logger.info(f"处理失败: {exc}")

# ✅
logger.info("progress.updated", user_id=str(user_id), node_id=str(node_id), status=new_status)
logger.error("progress.update_failed", node_id=str(node_id), error=str(exc))
```

**事件名约定**：`<模块>.<动作>`，小写下划线

| 事件 | 何时记录 |
|---|---|
| `http.request` | 每个请求（中间件自动） |
| `progress.updated` | 进度变更 |
| `ai.call` | 每次 LLM 调用 |
| `ai.degraded` | 降级发生 |
| `ai.circuit_opened` | 熔断器打开 |
| `job.created` / `job.succeeded` / `job.failed` | 异步作业生命周期 |
| `cycle_detected` | 检测到依赖环（说明有 bug 或被人工改坏） |

**禁止记录**：

- API Key
- 完整 prompt
- 用户笔记全文

见 `06-AI能力设计.md` §8.2 的脱敏 processor。

### 2.6 异常规范

```python
# ❌ 裸 except
try:
    ...
except:
    pass

# ❌ 捕获 Exception 后什么都不做
try:
    ...
except Exception:
    logger.error("failed")

# ✅ 捕获具体异常 + 记录上下文 + 明确处理
try:
    result = await self.llm.complete_json(...)
except LLMTimeoutError as exc:
    logger.warning("ai.degraded", feature="next_step", reason="timeout")
    return self._rule_based_fallback()
except LLMInvalidOutputError as exc:
    logger.error("ai.invalid_output", feature="next_step", error=str(exc))
    return self._rule_based_fallback()
```

**业务异常必须继承 `AppError`**（见 `04-后端设计.md` §1.3），这样全局处理器能统一转成标准错误响应。

### 2.7 注释规范

**只写"为什么"，不写"是什么"。**

```python
# ❌ 废话注释
# 查询节点
nodes = await self.repo.list_startable(route_id, user_id)

# ✅ 解释意图
# 用 NOT EXISTS 而不是 COUNT：找到第一个未满足的前置就短路返回，
# 在有大量前置的节点上性能差异明显
nodes = await self.repo.list_startable(route_id, user_id)
```

**必须写注释的地方**：

1. 绕过常规做法的代码（说明为什么）
2. 有性能考量的代码
3. 有安全考量的代码
4. 边界条件处理
5. TODO / FIXME（必须带日期和你的名字）

```python
# TODO(2026-10-12): 目前用固定阈值 0.35，等有了测试集再调优
SIMILARITY_THRESHOLD = 0.35

# FIXME(2026-10-12): 并发下 next_message_seq 不安全，单用户场景暂时可接受
```

## 3. TypeScript / Vue 规范

### 3.1 ESLint + Prettier

**`frontend/.prettierrc`**

```json
{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all",
  "arrowParens": "always",
  "endOfLine": "lf"
}
```

**注意 `semi: false`**：不写分号。如果你不习惯，可以改成 `true`，但**全项目必须统一**。

### 3.2 TS 规范

**`tsconfig.json` 关键配置**

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "verbatimModuleSyntax": true,
    "paths": { "@/*": ["./src/*"] }
  }
}
```

**`noUncheckedIndexedAccess`** 会让 `arr[0]` 的类型变成 `T | undefined`。一开始会觉得烦，但它能防住大量"数组越界"的运行时错误。

**禁止 `any`**：

```ts
// ❌
function parse(data: any) { }

// ✅ 真的不确定时用 unknown + 收窄
function parse(data: unknown) {
  if (typeof data !== 'object' || data === null) throw new Error('invalid')
  // 现在可以安全访问了
}

// ✅ 已知结构
function parse(data: NodeProgress) { }
```

**类型导入用 `import type`**（`verbatimModuleSyntax` 要求）：

```ts
import type { RoadmapNode } from '@/types/api'
import { computed } from 'vue'
```

### 3.3 Vue 组件规范

**统一用 `<script setup lang="ts">`，顺序固定：**

```vue
<script setup lang="ts">
// 1. imports
import { ref, computed } from 'vue'
import type { RoadmapNode } from '@/types/api'

// 2. props / emits / slots
const props = defineProps<{ node: RoadmapNode; expanded?: boolean }>()
const emit = defineEmits<{ toggle: [nodeId: string]; expand: [nodeId: string] }>()

// 3. 组合式函数
const routeStore = useRouteStore()

// 4. 状态
const loading = ref(false)

// 5. 计算属性
const statusLabel = computed(() => STATUS_LABEL[props.node.progress.status])

// 6. 方法
function handleToggle() {
  emit('toggle', props.node.id)
}

// 7. 生命周期
onMounted(() => { /* ... */ })
</script>

<template>
  <!-- 模板放最后 -->
</template>

<style scoped>
/* 样式放最后 */
</style>
```

**组件命名**：文件名 `PascalCase.vue`，模板里用 `PascalCase` 或 `kebab-case` 都可以，但**保持一致**。推荐模板里也用 `PascalCase`（能在编辑器里点击跳转）。

**Props 用类型声明而不是运行时对象**：

```ts
// ✅
const props = defineProps<{
  node: RoadmapNode
  expanded?: boolean
}>()

// ❌
const props = defineProps({
  node: { type: Object, required: true },
})
```

**v-for 必须有 key，且不要用 index**：

```vue
<!-- ✅ -->
<NodeRow v-for="node in nodes" :key="node.id" :node="node" />

<!-- ❌ index 会导致状态错乱 -->
<NodeRow v-for="(node, i) in nodes" :key="i" :node="node" />
```

**不要用 `v-if` 和 `v-for` 在同一个元素上**（Vue 3 里 `v-if` 优先级更高，行为反直觉）：

```vue
<!-- ❌ -->
<div v-for="n in nodes" v-if="n.visible" :key="n.id">

<!-- ✅ -->
<template v-for="n in nodes" :key="n.id">
  <div v-if="n.visible">
</template>
```

### 3.4 Pinia 规范

用 setup 语法（`defineStore('name', () => {...})`）而不是 options 语法，风格和组件统一。

```ts
export const useFooStore = defineStore('foo', () => {
  const items = ref<Item[]>([])
  const loading = ref(false)

  const count = computed(() => items.value.length)

  async function load() { /* ... */ }

  return { items, loading, count, load }
})
```

**规则**

- store 只存跨组件共享的状态（见 `05-前端设计.md` §5.1）
- **不要在 store 里直接操作 DOM 或路由**（保持可测试）
- store 之间可以互相调用，但避免循环依赖

### 3.5 API 层规范

**每个后端资源对应一个 api 文件**，函数名和接口语义一致。

```ts
// src/api/progress.ts
import { client } from './client'
import type { NodeProgress, NodeStatus } from '@/types/api'

export interface ProgressUpdatePayload {
  status: NodeStatus
  mastery?: number
}

export interface ProgressUpdateResult extends NodeProgress {
  node_id: string
  unlocked_nodes: Array<{ id: string; title: string }>
}

export function updateProgress(
  nodeId: string,
  payload: ProgressUpdatePayload,
  signal?: AbortSignal,
) {
  return client
    .put<ProgressUpdateResult>(`/nodes/${nodeId}/progress`, payload, { signal })
    .then((r) => r.data)
}
```

**规则**

- 返回 `r.data`，不要返回整个 `AxiosResponse`
- 支持传入 `AbortSignal`（需要取消能力的接口）
- 类型从 `@/types/api` 导入，不要在每个 api 文件里重复定义

## 4. 测试规范

### 4.1 测试分层

| 层 | 目录 | 依赖 | 速度 | 覆盖目标 |
|---|---|---|---|---|
| 单元 | `tests/unit/` | 无外部依赖 | 毫秒级 | 纯逻辑函数、schema 校验 |
| 集成 | `tests/integration/` | 真实 PostgreSQL | 秒级 | repository、service |
| 端到端 | `tests/e2e/` | 完整服务 | 十秒级 | 关键用户路径（可选） |

**MVP 阶段至少要 unit + integration。** E2E 可以到 M10 再补。

### 4.2 必须写测试的地方

见 `04-后端设计.md` §7.1，五处：

1. 依赖环检测
2. 推荐算法
3. 用户数据隔离
4. AI 输出校验与降级
5. 进度状态流转 + 复习调度

### 4.3 测试命名

**测试名应该是一句"期望行为的描述"。**

```python
# ❌
def test_cycle():
    ...

# ✅
async def test_direct_cycle_is_rejected():
    """A→B 已存在时，再添加 B→A 必须被拒绝"""

async def test_diamond_dependency_is_not_a_cycle():
    """A→B, A→C, B→D, C→D 是合法的菱形依赖，不是环"""
```

格式：`test_<被测对象>_<条件>_<期望结果>`

### 4.4 Fixture 规范

```python
# tests/conftest.py
import pytest
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine, async_sessionmaker

@pytest.fixture(scope="session")
def test_engine():
    engine = create_async_engine("postgresql+asyncpg://routebook:routebook@localhost:5432/routebook_test")
    yield engine

@pytest.fixture
async def session(test_engine) -> AsyncIterator[AsyncSession]:
    """每个测试用例一个事务，测试结束回滚 —— 测试之间完全隔离。"""
    async with test_engine.connect() as conn:
        trans = await conn.begin()
        session = async_sessionmaker(bind=conn, expire_on_commit=False)()
        try:
            yield session
        finally:
            await session.close()
            await trans.rollback()


@pytest.fixture
async def make_nodes(session):
    """工厂 fixture：批量创建测试节点。"""
    created = []

    async def _make(count: int, route_id: UUID | None = None):
        nodes = [Node(id=uuid4(), route_id=route_id or default_route_id,
                      title=f"节点 {i}", module_name="测试模块") for i in range(count)]
        session.add_all(nodes)
        await session.flush()
        created.extend(nodes)
        return nodes

    yield _make
```

**`make_nodes` 这类工厂 fixture 比一堆硬编码的 fixture 更好用**，因为测试需要的数据形态很多变。

### 4.5 测试数据隔离

**`conftest.py` 里必须有断言，防止测试连到生产库**：

```python
@pytest.fixture(scope="session", autouse=True)
def assert_test_database():
    url = settings.DATABASE_URL
    if "test" not in url:
        pytest.exit(f"拒绝在非测试数据库上运行测试：{url}")
```

**这条断言能救你的命。** 没有它，某个配置错误就可能导致测试把生产数据清空。

## 5. 文档维护

### 5.1 什么时候必须更新文档

| 变更 | 要更新的文档 |
|---|---|
| 改接口字段 | `04-后端设计.md` |
| 改表结构 | `02-领域模型与数据库设计.md` |
| 改技术选型 | `03-技术架构.md`（并加一条 ADR） |
| 改 prompt 契约 | `06-AI能力设计.md` |
| 改里程碑范围 | `08-开发计划.md` |
| 改产品功能 | `01-产品设计.md` |

### 5.2 文档与代码冲突时

**以文档为准，先改文档再改代码。**

理由：文档是设计意图，代码是实现。如果代码偏离了设计，要么是设计错了（该改文档），要么是实现错了（该改代码）。**但必须先明确是哪种**，不能含糊地"以实际代码为准"。

### 5.3 ADR（架构决策记录）

**任何"以后可能会有人问为什么这么选"的决定，都要写一条 ADR。**

放在 `docs/adr/` 目录，格式：

```markdown
# ADR-006：用轮询而不是 WebSocket 获取异步任务状态

- **状态**：已采纳
- **日期**：2026-10-20
- **背景**：（是什么问题促使我们做这个决定）
- **决策**：（我们决定做什么）
- **理由**：（为什么选这个方案，放弃了什么）
- **后果**：（这个决定带来了什么好处和代价）
- **重新评估的条件**：（什么情况下应该重新考虑）
```

**判断标准**：如果你在写代码时需要停下来想"当初为什么这么设计"，那这个决定就该有 ADR。

## 6. 依赖管理

### 6.1 添加依赖的原则

**加依赖前先问三个问题：**

1. 标准库或现有依赖能不能做到？
2. 这个库还在维护吗？（看最近一次 commit）
3. 它引入了多少个间接依赖？（`uv tree` 看）

**能自己写 50 行搞定的，不要引依赖。**

### 6.2 锁文件

| 文件 | 必须提交 | 说明 |
|---|---|---|
| `backend/uv.lock` | ✅ | 保证依赖版本一致 |
| `frontend/pnpm-lock.yaml` | ✅ | 同上 |

```bash
# 后端：按 lock 精确安装（CI 用）
uv sync --frozen

# 前端：同上
pnpm install --frozen-lockfile
```

### 6.3 依赖更新

**每月做一次，不要等到出事。**

```bash
# 后端：查看可更新项
uv lock --upgrade
uv run pytest

# 前端
pnpm outdated
pnpm update --latest
pnpm type-check && pnpm build
```

**更新后必须跑完整测试。** 如果测试挂了，先判断是"依赖升级导致的破坏性变更"，还是"测试本身太脆弱"。
