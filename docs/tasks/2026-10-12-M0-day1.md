### 2.3 验收（逐个服务）

| 服务 | 验收方式 | 期望 |
|---|---|---|
| db | `docker compose -f deploy/docker-compose.dev.yml exec db psql -U routebook -d routebook -c "select 1"` | 返回一行 1 |

| flower | 浏览器打开 `http://localhost:5555` | 能打开 |

**关键验证（M1 就靠它）**：

```bash
docker compose -f deploy/docker-compose.dev.yml exec db psql -U routebook -d routebook -c "CREATE EXTENSION IF NOT EXISTS vector; SELECT extname FROM pg_extension;"
```

能看到 `vector` 说明你用的镜像是对的（`pgvector/pgvector:pg16`）。**用官方 `postgres:16` 镜像就没有这个扩展，M1 会直接卡住。**

### 2.4 这一步常见的三个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| flower 容器起不来 / 拉不到镜像 | 镜像 tag 失效，或暂时不需要 | **先在 compose 里注释掉 flower**，M8 才用得上，不影响 M0 验收 |
| `port 5432 already in use` | 本机已装了 PostgreSQL | 把宿主机端口改成 `5433:5432`，同时改 `.env` 里的 `DATABASE_URL` 端口 |
| `port 6379 in use` | 本机已装了 Redis | 同理改成 `6380:6379` |

## 步骤 3 · 后端骨架（90 min）

### 3.1 初始化项目

```bash
cd /d/workplace/code/Routebook/backend
uv init --package --name routebook
```

**然后必须验证包的 import 路径是对的**（这一步比记住参数重要）：

期望打印出 `.../backend/src/routebook/__init__.py`。如果打印的是别的位置，说明目录布局不对——停下来先把它改对，不然后面所有 import 都会错。

### 3.4 启动与验收

```bash

```

| 验收 | 命令 / 方式 | 期望 |
|---|---|---|
| 接口通 | `curl http://localhost:8000/health` | `{"status":"ok",...}` |

## 步骤 4 · 前端骨架（90 min）

### 4.1 初始化

```bash
cd /d/workplace/code/Routebook
pnpm create vite frontend --template vue-ts
cd frontend
pnpm install
pnpm add vue-router pinia axios naive-ui
pnpm add -D @types/node openapi-typescript
```

### 4.2 配置

| 事项 | 要求 |
|---|---|
| `tsconfig.json` | `"strict": true`，并加路径别名 `"@/*": ["./src/*"]` |
| `vite.config.ts` | 加 `@` 别名（要与 tsconfig 一致）+ `/api` 代理到 `http://localhost:8000` |
| `.env.development` | `VITE_API_BASE_URL=/api/v1` |
| `package.json` | 加 `"type-check": "vue-tsc --noEmit"` |

**代理配置的验证方式**：浏览器访问 `http://localhost:5173/api/health`，应该返回后端的 JSON——**如果这一步通了，说明代理配对了**（注意代理规则用 `/api` 前缀重写，别把 `/api` 也转发给后端）。

**要自己想清楚**：为什么前端不直接请求 `http://localhost:8000`？——这是 CORS 问题，也是生产环境同源部署的基础。想明白这一条，你就理解了为什么 `.env` 里 `CORS_ORIGINS=http://localhost:5173`。

### 4.3 写代码（5 个文件）

| 文件 | 内容 |
|---|---|
| `src/api/client.ts` | Axios 实例：`baseURL` 从 `import.meta.env.VITE_API_BASE_URL` 读；响应拦截器统一解包 / 报错 |
| `src/main.ts` | 挂载 pinia + router |
| `src/App.vue` | 只放 `<RouterView />` |
| `src/views/HealthView.vue` | onMounted 调 `/health`，把 `status` 显示在页面上，带 loading 和 error 两个状态 |
| `src/api/health.ts` | 定义 `healthApi()` 和返回类型 |

**注意**：`VITE_API_BASE_URL=/api/v1` 而后端 `/health` 在 `/api/health`——所以 health 要么单独配 URL，要么今天先把它放在 `/api/v1/health` 下。

**今天就要做决定的地方**：`/health` 到底挂在 `/api/health`（运维探针，不进版本）还是 `/api/v1/health`（业务接口，进版本）。建议 **探针类放 `/api/health`、业务接口全部在 `/api/v1/` 下**，然后在 `client.ts` 里额外导出一个不带 `/v1` 的裸客户端给探针用。

### 4.4 验收

```bash
pnpm dev
pnpm type-check      # 必须 0 error
pnpm build           # 必须成功
```

页面验收：
- [ ] 打开 `http://localhost:5173`，页面上显示 `ok`
- [ ] 浏览器控制台**无红色报错**
- [ ] 网络面板里能看到那次请求，**返回 200**
- [ ] 后端终端里能看到这次请求的日志（说明真的打到了后端，不是前端自己编的）

**故意做个实验**：把后端 `/health` 的返回值改成 `status: "degraded"`，刷新页面看是否跟着变；再把后端停掉，看页面是否显示错误提示而不是白屏。**这一步是在验证你的错误处理真的接上了**，比看到 `ok` 更有价值。
